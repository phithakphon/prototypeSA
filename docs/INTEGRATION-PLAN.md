# 🔀 แผนรวมงานจาก `origin/main` เข้ากับสาขา PostgreSQL

> **สถานะ: ยังไม่ได้ merge และยังไม่ได้แก้โค้ดของเพื่อนร่วมทีม** เอกสารนี้เป็นผลวิเคราะห์และแผนที่เสนอให้ตัดสินใจก่อนลงมือ
> ตรวจจากสภาพจริงของ `origin/main` (`2a69c71`) เทียบกับ `feature/register-page`

## สรุปสั้น

`main` ล้ำหน้าสาขานี้ 4 commit (PR #3 และ #4) เพิ่ม **ระบบผลการประเมินพนักงาน** ที่เขียนบน **SQLite แบบ synchronous**
ส่วนสาขานี้ย้ายทั้ง backend ไปใช้ **PostgreSQL (Supabase) แบบ asynchronous** แล้ว จึง:

- Git รวมอัตโนมัติไม่ได้: **conflict 5 ไฟล์**
- ต่อให้แก้ conflict แล้ว **โค้ดประเมินผลทำงานไม่ได้** (เรียก `db.prepare().get()` แบบ synchronous บนชั้น DB ที่เปลี่ยนเป็น `await db.query()`)
- มีอีกจุดที่ต้องให้ทีมตัดสินใจ: ออกแบบ "การสมัครบัญชีพร้อมขอบทบาท" บน `main` ต่างจากแนวทาง "สมัครเป็นพนักงาน แล้วฝ่ายบุคคลผูกบัญชี" ในสาขานี้

ดังนั้นระบบรวมของทีม **ยังไม่พร้อม deploy** จนกว่าจะทำตามแผนนี้

## 1. Conflict ระหว่างสองสาขา

ทดลอง `git merge --no-commit origin/main` แล้วยกเลิกทันที (ไม่มีการเปลี่ยนแปลงถาวร)

| ไฟล์ | ชนิด | สาเหตุ |
|---|---|---|
| `backend/package.json` | conflict | `test` script และ `seed:evaluations` เทียบกับ script ใหม่ (PostgreSQL, bootstrap ฯลฯ) |

| `backend/src/rbac.js` | conflict | `main` เพิ่ม `evaluation:view/manage`; สาขานี้ปรับสิทธิ์ใหม่ (`selfOnly`, `salary:view`, `account:link`) |
| `frontend/src/AppRoutes.jsx` | conflict | `main` แทน `ComingSoon` ด้วย `Evaluations`; สาขานี้เพิ่ม route `/accounts` ใกล้จุดเดียวกัน |

## 2. ความไม่เข้ากันของระบบผลการประเมิน กับ PostgreSQL

| ชิ้นงานบน `main` | ปัญหา | สิ่งที่ต้องเปลี่ยน |
|---|---|---|
| `backend/src/routes/evaluations.js` | ใช้ `db.prepare(...).get/all/run`, placeholder `?`, `lastInsertRowid` แบบ SQLite และ helper `employee()` แบบ synchronous | เปลี่ยนเป็น `await db.query(..., [$1...])`, `INSERT ... RETURNING id`, `upper(employee_code) = $1`, ทำ handler/helper เป็น async; ใช้ `getEmployee`-style ที่เคารพ **ขอบเขตแผนก** และ `employee:selfOnly` (ปัจจุบันค้นหาด้วยรหัสพนักงานทุกแผนกได้) |
| `backend/src/migrations/005_performance_evaluations.sql` | ไวยากรณ์ SQLite (`AUTOINCREMENT`, `TEXT` เป็นวันที่, `datetime('now')`) | เขียนไฟล์ PostgreSQL ชื่อเดิม `005_performance_evaluations.sql`: `INTEGER GENERATED BY DEFAULT AS IDENTITY`, `DATE`, `TIMESTAMPTZ DEFAULT now()`, คง `CHECK (score_N BETWEEN 1 AND 5)` และ index เดิม **เพิ่ม** `ENABLE ROW LEVEL SECURITY` + revoke จาก `anon`/`authenticated` (กฎเดียวกับทุกตาราง) |
| `backend/src/migrations/sqlite/003_account_registration.sql`, `004_backend_only_access.sql` | เป็น override เฉพาะ SQLite และ `003` เพิ่ม `users.requested_role` + ตาราง `account_role_history` ซึ่ง **ไม่มีโค้ด backend/UI รองรับบน `main`** | เมื่อใช้ PostgreSQL ไม่จำเป็นต้องมีโฟลเดอร์ `sqlite/` — ดูหัวข้อ "ต้องให้ทีมตัดสินใจ" |
| `backend/src/demo-evaluation-seed.js` | ใช้ `db.prepare` และ `transaction(db, fn)` แบบ synchronous | เขียนเป็น async ด้วย `db.transaction(async (tx) => ...)`; คงเงื่อนไขเดิม (ตรวจตัวตนก่อนเพิ่ม, เพิ่มอย่างเดียว, รันซ้ำได้, ไม่สร้างพนักงาน) |
| `backend/src/seed-evaluations.js` | เปิดไฟล์ SQLite ผ่าน `DB_PATH` | ใช้ `DATABASE_URL` + `createDb` และกลไกป้องกัน seed ระยะไกลเดิม (`ALLOW_REMOTE_SEED`, ห้ามเมื่อ production) |
| `backend/test/evaluations.test.js` และเทสต์ใน `api.test.js` | สร้างไฟล์ SQLite ชั่วคราว, `db.exec`, รีสตาร์ท server เพื่อทดสอบการเก็บถาวร | ย้ายไปใช้ `createTestDb()` (PostgreSQL ในหน่วยความจำ), ทดสอบการคงอยู่ด้วยการสร้าง app ใหม่บน DB เดิม; ใช้ glob `test/*.test.js` แทนรายชื่อไฟล์ |
| `shared/evaluations.js`, `shared/demoEvaluations.js` | ฟังก์ชันล้วน ไม่เกี่ยวกับฐานข้อมูล | **ใช้ได้ทันที** ไม่ต้องแก้ |
| `frontend/src/pages/Evaluations.jsx` + test | เรียก API ผ่าน `api()` เท่านั้น | ใช้ได้ทันที (ตรวจเมนูหลังรวม) |
| `frontend/integration/*` + `run.mjs` | `run.mjs` import `openDb(url, { options })` และเรียก `admin.query()`/`migrate(db)` แบบ async บนฐาน PostgreSQL (ต้องมี `TEST_DATABASE_URL`) ซึ่ง `main` เองก็ยังไม่มี (ชั้น DB บน `main` ยังเป็น SQLite) และ `register.test.jsx` อ้างฟิลด์ "บทบาทที่ต้องการ" ที่ไม่พบใน `Register.jsx` บน `main` | ต้องปรับให้ใช้ `createDb`/`createTestDb` ของสาขานี้ หรือสอบถามเจ้าของว่าจะเก็บแนวทางไหน — ไม่ได้ทดลองรันชุดนี้ |

### ข้อมูลเดิมจะถูกลบหรือไม่?

**ไม่** ฐานข้อมูล Supabase ปัจจุบันยังไม่มีตารางผลการประเมิน การเพิ่มตารางด้วย migration แบบ "เพิ่มอย่างเดียว" จึงไม่แตะข้อมูลเดิม
ข้อมูลตัวอย่างผลการประเมินของเพื่อนอยู่ในไฟล์ SQLite ของเครื่องเขา (`backend/data/evaluation-demo.db`) ไม่กระทบกับ Supabase
ถ้าต้องการนำเข้า: ใช้ seed ตัวอย่างที่ย้ายเป็น PostgreSQL แล้ว (เฉพาะฐานข้อมูลทดสอบ)

## 3. สิ่งที่ต้องให้ทีมตัดสินใจก่อนลงมือ

1. **การสมัครบัญชี:** สาขานี้ = สมัครเป็นพนักงานเสมอ แล้วฝ่ายบุคคลผูกกับพนักงานและบัญชียังเป็นบทบาท `employee` (ไม่มีใครเลือกบทบาทเอง)
   ส่วน `main` มีร่องรอยของ "ขอบทบาทที่ต้องการ" (`requested_role`, `account_role_history`) แต่ **ยังไม่มีโค้ดใช้งานจริง**
   → แนะนำคงแนวทางของสาขานี้ (ปลอดภัยกว่า ไม่มีการยกระดับสิทธิ์จากการสมัคร) และถ้าต้องการให้ฝ่ายบุคคลเปลี่ยนบทบาทภายหลัง ให้ออกแบบเป็นฟีเจอร์ใหม่ที่มี audit
2. **ใครดูผลการประเมินได้:** `main` กำหนด `evaluation:view` = employee, manager และ `evaluation:manage` = manager ควรยืนยันว่า HR/executive ไม่ต้องดู
   และพนักงานดูได้เฉพาะของตนเอง (โค้ดเดิมบังคับแล้ว)
3. **ขอบเขตแผนก:** ผลการประเมินของพนักงานนอกแผนกตรวจสอบบัญชีควรมองไม่เห็นเช่นเดียวกับส่วนอื่น (แนะนำให้ใช้กฎเดียวกัน)
4. **โฟลเดอร์ `migrations/sqlite/`:** เมื่อใช้ PostgreSQL อย่างเดียว ควรลบหรือย้ายไป `legacy-sqlite/` (สาขานี้ย้าย schema SQLite เดิมไว้ที่นั่นแล้ว)

## 4. แผนรวมงานที่ปลอดภัย (เสนอให้อนุมัติ)

ทุกขั้นทำบนสาขาแยก ไม่ force push ไม่แตะ `main` ไม่รัน migration กับ Supabase จนกว่าจะอนุมัติ

1. สร้างสาขา `integration/main-into-postgres` จาก `feature/register-page`
2. `git merge origin/main` — แก้ conflict 5 ไฟล์ โดย **คงโค้ดของทั้งสองฝ่าย**: รวม script, รวมสิทธิ์ (`evaluation:*` + สิทธิ์ใหม่), รวม route/handler ของ frontend; `migrate.js` ใช้ฉบับ PostgreSQL ของสาขานี้
3. ย้าย `evaluations.js`, migration `005`, seed ตัวอย่าง และเทสต์ไปใช้ PostgreSQL ตามตารางข้อ 2 โดยไม่เปลี่ยนรูปแบบ API (`GET /api/evaluations/employee`, `GET/POST /api/evaluations`) เพื่อไม่ให้หน้า `Evaluations.jsx` ของเพื่อนกระทบ
4. ปรับเทสต์ของเพื่อนให้รันบน PGlite และเพิ่มเทสต์ RBAC/ขอบเขตแผนก/การเก็บถาวร ให้ครอบคลุมเท่าเดิมหรือมากกว่า
5. รันทุกอย่าง: backend tests, frontend tests, lint, build; ตรวจ migration `005` บน PGlite (ตาราง + RLS) และ dry-run แบบอ่านอย่างเดียวกับ Supabase
6. **ขออนุมัติ** รัน `npm run migrate` กับ Supabase (เพิ่มตาราง `performance_evaluations` เท่านั้น) หลังสำรองข้อมูล
7. เปิด PR เข้า `main` ให้เพื่อนร่วมทีม review (ผู้เขียนฟีเจอร์ประเมินผลควรตรวจส่วนที่ย้าย) ห้าม merge เองก่อนได้รับอนุมัติ

ประมาณงาน: โค้ดและเทสต์ราว 1 วันทำงาน บวกเวลาตัดสินใจข้อ 3 และ review
