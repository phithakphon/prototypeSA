# Backend — Employee Management System

Express REST API + PostgreSQL (Supabase). ผู้ใช้เรียกผ่าน `React → Express → Supabase PostgreSQL` เท่านั้น
Frontend ไม่เคยถือ credential ของฐานข้อมูล

## สถาปัตยกรรมฐานข้อมูล

| | เดิม | ปัจจุบัน |
|---|---|---|
| ฐานข้อมูล | SQLite (`node:sqlite`) ไฟล์ `backend/data/app.db` | PostgreSQL บน Supabase |
| การเชื่อมต่อ | `src/db.js` (`DatabaseSync`, synchronous) | `src/db.js` (`pg` Pool, async, parameterized `$1..$n`) |
| Schema | `src/legacy-sqlite/001_init.sqlite.sql` (เก็บไว้อ้างอิง) | `src/migrations/001_init.sql` |
| Auth | JWT (HS256) + bcrypt ของ Express เอง | **เหมือนเดิม** (ไม่ใช้ Supabase Auth) |

Migration: `001_init.sql` (schema), `002_reinstated_and_username_ci.sql` (event `reinstated` + username ไม่ซ้ำแบบไม่สนตัวพิมพ์), `003_account_links.sql` (1 พนักงาน : 1 บัญชี + ตาราง audit การผูกบัญชี)
ตาราง: `employees`, `users`, `salaries`, `employee_history`, `announcements`, `schema_migrations`
ชนิดข้อมูลที่ต่างจาก SQLite: id เป็น `INTEGER GENERATED BY DEFAULT AS IDENTITY`, วันที่เป็น `DATE`, เงินเดือนเป็น `NUMERIC(12,2)`,
เวลาเป็น `TIMESTAMPTZ` — แต่ `db.js` แปลงกลับให้ JSON เหมือนเดิม (วันที่เป็นสตริง `YYYY-MM-DD`, เงินเป็นตัวเลข)

**ความปลอดภัยฝั่ง Supabase:** ทุกตารางเปิด Row Level Security โดยไม่มี policy (deny) และ revoke สิทธิ์จาก role `anon`/`authenticated`
จึงเรียกผ่าน Supabase REST API ด้วย anon key ไม่ได้ ข้อมูลเข้าถึงได้ผ่าน Express เท่านั้น (Express ใช้ role เจ้าของฐานข้อมูล
ซึ่งข้าม RLS) การตรวจสิทธิ์ตามบทบาท (`src/rbac.js`) ยังบังคับที่ backend ทั้งหมด

## ตัวแปรสภาพแวดล้อม (`.env`)

| ตัวแปร | จำเป็น | ความหมาย |
|---|---|---|
| `JWT_SECRET` | ใช่ | คีย์เซ็น JWT (สร้างตามคำสั่งใน `.env.example`) |
| `DATABASE_URL` | ใช่ | connection string ของ Supabase (รหัสผ่านที่มีอักขระพิเศษต้อง URL-encode) |
| `DB_SSL` | ไม่ | `disable` / `require` / `verify` (ค่าเริ่มต้น: localhost = disable, อื่น ๆ = require) |
| `DB_SSL_CA` | ไม่ | path ของ CA cert ใช้เมื่อ `DB_SSL=verify` |
| `DB_POOL_MAX` | ไม่ | จำนวน connection สูงสุด (10) |
| `AUTO_MIGRATE` | ไม่ | `true` = รัน migration ตอนสตาร์ท (ค่าเริ่มต้น false) |
| `PORT`, `JWT_EXPIRES_IN` | ไม่ | 3001, 8h |
| `SQLITE_PATH` | ไม่ | ใช้กับ `migrate:data` เท่านั้น (ค่าเริ่มต้น `./data/app.db`) |

ห้าม commit `.env` (อยู่ใน `.gitignore` แล้ว รวมถึง `data/` และ `*.db`) — `.env.example` มีแต่ค่า placeholder

## ตั้งค่า Supabase

1. สร้างโปรเจกต์ที่ supabase.com และตั้ง Database password
2. Dashboard → **Connect** → คัดลอก connection string แบบ **Session pooler** (พอร์ต 5432) ใส่ `DATABASE_URL`
   (Transaction pooler พอร์ต 6543 ก็ใช้ได้ — โค้ดไม่ใช้ named prepared statement)
3. (แนะนำ) Database Settings → SSL Configuration → ดาวน์โหลด **Supabase Root 2021 CA** เก็บนอก git แล้วตั้ง `DB_SSL=verify` และ `DB_SSL_CA=<path>`
   - ใบรับรองของ Supabase ออกโดย CA ของ Supabase เอง ไม่อยู่ใน trust store ของ Node จึงต้องระบุ CA (ไม่ระบุแล้ว verify จะได้ `SELF_SIGNED_CERT_IN_CHAIN`)
   - **ห้ามเชื่อใบรับรองที่ดึงมาจากเซิร์ฟเวอร์ฐานข้อมูลเอง** ต้องดาวน์โหลดจาก Supabase Dashboard เท่านั้น แล้วเทียบ SHA-256 ที่ Dashboard แสดงกับค่าที่สคริปต์ตรวจพิมพ์ออกมา
   - วางไฟล์ไว้ที่ `backend/certs/` (อยู่ใน `.gitignore` ไม่ถูก commit) แล้วใส่ใน `.env`: `DB_SSL=verify` และ `DB_SSL_CA=./certs/<ชื่อไฟล์>.crt`
   - ตรวจด้วย `npm run db:ssl-check` — แสดงข้อมูลและ SHA-256 ของไฟล์ CA, ตรวจว่าเป็น Root CA ที่ยังไม่หมดอายุ แล้วลองเชื่อมต่อแบบ verify (`SELECT 1`)
   - ถ้าไม่ตั้ง จะใช้ `require` (เข้ารหัส แต่ไม่ตรวจใบรับรองเซิร์ฟเวอร์) และ server จะเตือนตอนสตาร์ท
   - `NODE_ENV=production` **บังคับ** `DB_SSL=verify` มิฉะนั้นไม่เริ่มทำงาน
   - พารามิเตอร์ SSL ใน `DATABASE_URL` (เช่น `?sslmode=`) ถูกตัดทิ้ง เพื่อไม่ให้ลดระดับความปลอดภัยโดยไม่ตั้งใจ
4. ใช้ **โปรเจกต์ทดสอบ/dev แยกต่างหาก** ก่อนใช้งานจริง

## การใช้งาน

```bash
cd backend
npm install
cp .env.example .env      # แก้ JWT_SECRET และ DATABASE_URL
npm run migrate           # สร้างตาราง (ไม่เขียนทับตารางที่มีอยู่: ถ้ามีตารางชื่อเดียวกันแล้วจะ fail และ rollback)
npm run seed              # ข้อมูลทดสอบ — บล็อกเมื่อ DB เป็นระยะไกล เว้นแต่ ALLOW_REMOTE_SEED=yes
npm start                 # ตรวจการเชื่อมต่อ + migration ที่ค้างก่อนเปิดพอร์ต
```

Local development ที่ไม่ใช้ Supabase: ติดตั้ง PostgreSQL เองแล้วตั้ง
`DATABASE_URL=postgresql://user:pass@localhost:5432/ems` (SSL ปิดอัตโนมัติเมื่อเป็น localhost)

## ย้ายข้อมูลจาก SQLite เดิม

```bash
npm run migrate:data                                        # DRY RUN: อ่าน SQLite อย่างเดียว แสดงจำนวนแถวต่อตาราง ไม่แสดงค่า ไม่เขียนอะไร
npm run migrate:data -- --execute --approve-pii-transfer    # ย้ายจริง (ต้องมีทั้งสอง flag)
```

- ข้อมูลที่จะถูกย้าย: `employees` (รวมเลขบัตรประชาชน เบอร์โทร อีเมล ที่อยู่), `users` (รวม bcrypt password hash),
  `salaries`, `employee_history`, `announcements` — **เป็นข้อมูลอ่อนไหว ให้ตรวจ dry run และอนุมัติก่อนทุกครั้ง**
- เก็บ id เดิมและความสัมพันธ์ทั้งหมด, เปิด SQLite แบบ read-only (ไม่แก้/ไม่ลบไฟล์เดิม)
- รันซ้ำได้: `ON CONFLICT (id) DO NOTHING` ไม่ซ้ำและไม่เขียนทับ; ทั้งหมดอยู่ใน transaction เดียว
  ถ้า unique key ชนกับแถวที่มี id ต่างกัน (เช่น `employee_code` ซ้ำ) จะ rollback ทั้งชุด
- ต้อง `npm run migrate` ก่อน; ปรับ sequence ของ id ให้ต่อจาก id ที่นำเข้า

## เปลี่ยนรหัสผ่านบัญชีทดสอบ (rotate)

```bash
# ตั้งรหัสผ่านใหม่ชั่วคราวใน .env: ROTATE_NEW_PASSWORD=...  (อย่างน้อย 12 ตัว มีพิมพ์เล็ก/ใหญ่/ตัวเลข)
npm run rotate:passwords                                    # DRY RUN: ตรวจเงื่อนไข ไม่เขียนอะไร ไม่แสดงรหัสผ่าน
npm run rotate:passwords -- --execute --confirm-rotate      # เปลี่ยนจริง (transaction เดียว, bcrypt cost 10)
```

- แก้เฉพาะ `password_hash` ของ manager1, hr1, finance1, executive1, employee1 (ระบุเองได้ด้วย `ROTATE_USERNAMES=a,b`)
- ปฏิเสธรหัสผ่านที่สั้น อ่อน เป็นรหัสเริ่มต้นที่เปิดเผย ซ้ำ `SEED_PASSWORD` หรือเหมือนรหัสผ่านปัจจุบัน
- หลังเปลี่ยน: อัปเดตหรือลบ `SEED_PASSWORD` และลบ `ROTATE_NEW_PASSWORD` ออกจาก `.env`
- session (JWT) ที่ออกไปแล้วยังใช้ได้จนหมดอายุ (`JWT_EXPIRES_IN`) — ถ้าต้องการตัดทันทีให้เปลี่ยน `JWT_SECRET` แล้วรีสตาร์ท

## ผูกบัญชีที่สมัครเองกับพนักงาน

ฝ่ายบุคคล (`account:link`) ผูกที่หน้า `/accounts` หรือผ่าน API ระบบผูกได้เฉพาะบัญชีบทบาทพนักงานที่ยังไม่ผูก ไปยังพนักงานที่ยังปฏิบัติงาน
ในแผนกตรวจสอบบัญชี และยังไม่มีบัญชี (บังคับด้วย unique index) ต้องพิมพ์รหัสพนักงานยืนยัน บทบาทของบัญชีไม่เปลี่ยน และทุกครั้งถูกบันทึกใน
`account_link_audit` (ใครผูก/ยกเลิก บัญชีไหน พนักงานคนไหน เมื่อไร)

## แก้ปัญหาการเชื่อมต่อ

| อาการ | สาเหตุ / วิธีแก้ |
|---|---|
| `ต้องตั้งค่า DATABASE_URL` | ยังไม่ได้ตั้งใน `.env` (ไฟล์ `.env` เก่าที่มี `DB_PATH` ต้องเพิ่ม `DATABASE_URL`) |
| `DATABASE_URL รูปแบบไม่ถูกต้อง` | รหัสผ่านมี `@ : / ? #` → ต้อง URL-encode (`@` = `%40`) |
| `[28P01] password authentication failed` | รหัสผ่านหรือ username ผิด (pooler ใช้ `postgres.<project-ref>`) |
| `[ENOTFOUND]` / `[ETIMEDOUT]` | host ผิด, ไม่มีอินเทอร์เน็ต, หรือเครือข่ายไม่รองรับ IPv6 — ใช้ **Session pooler** แทน direct connection |
| `self-signed certificate in certificate chain` | ใช้ `DB_SSL=verify` โดยไม่มี `DB_SSL_CA` → ใส่ CA ของ Supabase หรือใช้ `DB_SSL=require` |
| `[53300]` / `too many clients` | ลด `DB_POOL_MAX` |
| API ตอบ 503 | ฐานข้อมูลเชื่อมต่อไม่ได้ชั่วคราว (ตรวจ log ฝั่งเซิร์ฟเวอร์ ซึ่งไม่พิมพ์ connection string) |
| `ยังมี migration ที่ยังไม่ได้รัน` | รัน `npm run migrate` |
